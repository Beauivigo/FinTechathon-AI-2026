# 项目本体审计与参赛要求差距

审计日期：2026-10-23。执行者：A / 独立审计。对象为本地 main 工作区，基线提交 `02fe7464c9b131a3b18722bd9df85a54227a0ee1` **加现有未提交修改**；不是仅审计该提交，也不代表 GitHub 已同步。

按用户最新要求，重点检查项目功能、安全、接口与执行流程，PPT、视频等材料不作为本次主要结论。本轮未修改业务代码或共享接口，未上传，未调用真实模型；原有成员文件及未提交修改保留。

## 结论

六个场景已有可运行的本地模拟业务基础，现有564项测试独立重跑全部通过。但新增故障注入复现了**两处会允许再次付款的上层流程缺陷**；计划持久化、真实身份验证和后台自动化也仍有差距。不能据现有回归结果认定“项目本体完全符合要求”或“没有漏洞”。

两处付款问题均仍需要用户再次确认；没有复现无授权直接扣款、同一幂等键重复扣款或底层资金事务失效。根因在跨页面状态协调与计划修订时丢失业务关联，不能把它们描述为已绕过银行强验证。

## 一、实际复现的缺陷

### AUD-01 / P1：AI待核实状态未覆盖手动页面

- **触发**：AI转账在银行端已经成功，但返回回执时发生异常，AI页面记录为 `unknown`、需要查询原操作。
- **现象**：切到手动转账页面仍可输入同一需求，产生新幂等键并再次确认付款。复现中两笔各20元，初始200000分变成196000分；原AI流程仍显示待核实。
- **原因**：[首页](../app/main.py#L44)只检查 `action_flow`；[公共业务页](../app/workflow.py#L35)只检查 `conversation`；[AI入口](../app/model_bank_panel.py#L41)也没有汇总其他会话的客户端未知结果。数据库已经成功的操作不会出现在未决状态过滤中，因此不能仅依赖数据库待办清单拦截。
- **影响**：用户可能误以为原操作未成功，换入口再付一次。这是跨入口防重复保护遗漏，第二笔仍需新确认。
- **最低修复验收**：所有业务入口统一核对 `conversation`、`action_flow`、`model_bank_flow` 的未决状态；双向切页均阻断新写操作，查询原操作成功后才恢复。保留原请求及幂等键，不能用清空会话来解锁。
- **证据**：[实际页面复现](evidence/project-audit-20261023/probes.json)、[复现脚本](evidence/project-audit-20261023/probes.py)。

### AUD-02 / P1：修改剩余计划会丢失已完成步骤

- **触发**：计划“给李明20元，再冻结卡片”，第一步完成后输入“第二步改为挂失，第一步已经办过了”。使用确定性模型返回同任务编号的更新后完整计划。
- **现象**：新计划将已付款的第一步重新列为待执行，已保存的回执集合变空；再次准备和确认后，原20元转账用新操作键重复付款。两笔共40元，卡片步骤尚未执行。
- **原因**：[页面接线](../app/model_bank_panel.py#L62)每逢草稿版本变化就新建执行器；[执行器初始化](../agent/model_bank.py#L165)清空 `receipts` 并将所有任务改为待执行，没有与可信的已完成步骤合并核对。禁止模型自行声明 `completed` 是正确边界，但不能因此丢弃后端已确认的完成事实。
- **影响**：局部修改后重新执行已完成的资金步骤；禁用“回退草稿”按钮没有覆盖普通补充消息。仍需再次确认，不是自动绕过授权。
- **最低修复验收**：计划修订保留已完成步骤及原操作键；已执行步骤内容发生变化时明确拒绝或转人工核对。既不能相信模型自报完成，也不能将已付款步骤自动视为新业务。覆盖改名、改编号、完整计划重发和依赖调整。
- **证据**：[复现结果](evidence/project-audit-20261023/plan-revision.json)、[实际页面复现脚本](evidence/project-audit-20261023/plan_revision_probe.py)。本用例不衡量真实模型产生这种回复的概率，而是证明程序没有挡住一种协议允许的回复。

## 二、功能与技术要求差距

### AUD-03 / P2：计划无法完整恢复，决策链审计信息不足

`DialogueSession` 和 `BankPlanRunner` 的任务、依赖、版本、回执映射主要保存在 Streamlit 会话内。银行单笔操作与定时任务有持久化，不等于整个AI计划已经持久化。

实际提交两步计划后，数据库只记录 `requested` / `accepted`，详情为版本、失败次数、阶段和意图；多任务计划的意图为null。没有保存规范化任务清单、依赖边及任务到操作键的映射，执行步骤事件也没有任务编号。见[审计入口](../bank/gateway.py#L45)及[复现记录](evidence/project-audit-20261023/probes.json)。因此仅凭数据库不能重建未执行计划和完整修改过程；页面会话重建后，单笔可以恢复，整体计划不能可靠续接。

最低补齐：服务端持久化经校验、脱敏的计划和版本、依赖、步骤状态、原操作关联及变更原因；重新打开页面后从后端恢复。记录结构化决策依据和执行事实即可，不要求保存模型隐含思考过程、完整提示、密钥或验证码。

### AUD-04 / 技术硬要求差距：目前仍是模拟验证

原技术要求截图将红色操作列为必须强验证，举例人脸、短信验证码、U盾等。当前[会话确认](../agent/controller.py#L168)调用[演示凭据签发](../bank/gateway.py#L409)，同一个可信页面程序生成凭据后立即提交；固定演示身份没有独立登录与真实第二因素。

现有实现能够证明“普通确认不能替代红色操作验证步骤”“挑战绑定、过期、单次使用和失败锁定有效”，**不能证明操作者通过了独立身份验证**。这不是本次发现的密钥泄露，也不是要求现在接真实银行；但没有主办方接受模拟验证的明确依据时，不能把它写成字面上完整满足该强制要求。

若后续实现真实验证，需要真实登录会话、独立验证器与用户/操作绑定、重放和失败限制；保留模拟模式并明确区分。当前审计不新增验证服务、不猜测外部服务接入规则。

### AUD-05 / 功能完整性差距：时间驱动业务仍需人工触发

当前有持久化定时转账和商户任务，也有本地订阅提醒；[转账调度](../bank/scheduler.py#L139)、[商户调度](../bank/merchant_scheduler.py#L65)与提醒检查由可信页面手动调用，没有持续后台执行器及外部通知交付。

因此“登记未来任务”“生日日期计划”“现在确认预算、下单”可演示；“生日当月自动锁定预算、提前两天主动执行采购、程序关闭仍按时提醒/推进”尚未完成。AI DAG把 `scheduled` 当作该登记步骤完成，也没有“等待未来实际执行结果再推进”的持久依赖机制。

后续补齐应包括可靠的到期检查、重启恢复、任务领取与重试、等待授权和失败人工接管；后台调度不能继承登记授权而绕过付款验证。这个缺口属于项目本体，不是需要B—E补历史截图才能解决的问题。
