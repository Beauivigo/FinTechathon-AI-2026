# 开发与需求阻塞处理规则

1. 优先推进现有需求明确、接口已确定的功能。
2. 缺少真实数据时，可以使用明确标记的模拟数据进行开发和测试。
3. 缺少业务规则时，不得自行编造或将假设作为正式业务逻辑。
4. 如果某功能因材料不足无法完成，记录：
    * 所属模块与业务动作
    * 当前已实现内容
    * 缺失的具体规则或数据
    * 需要负责人回答的问题
    * 是否影响其他模块开发
5. 对于阻塞功能，可以保留接口或未实现状态，继续推进不受影响的任务。
6. 统一维护 docs/BLOCKERS.md，记录所有待补材料和阻塞情况。
7. 不擅自修改已确定的共享接口和模块边界。

## 成员资料核验约定（2026-10-16 补充）

- README 固定展示 [成员资料勘误](成员资料勘误.md) 入口，主要在收到、核验、修订成员资料时更新。按日期与成员记录小错误、大错误、位置、依据、修正结果及状态，保留历史，不覆盖旧结论。
- 小错误指可依据现有事实修正的文字、版本、引用和不改变业务含义的计算引用问题；大错误指影响资金、权限、业务判断、接口语义或验收结论的问题。大错误即使可以修正，也须在当轮对话中明确提醒。
- 有现成依据的错误由 A 直接修正并告知；无法确定的业务规则不能自行补写。修订件保留来源与差异，原稿可保留作追溯依据。
- 2026-10-17补充：多数问题允许A自行修改更正，有明确契约/代码依据的大错误也可直接修正，并在对话提醒。只有涉及关键业务规则或无法据现有依据确定的抉择，才打回要求说明；不要仅因标为大错误就重复索要确认。
- 缺失日志、截图、测试记录等证据时，能够在本地复现的由 A 直接补测、保存可复现记录，不再单纯为补回历史附件退回成员。记录执行者、日期、代码版本、数据版本、命令、实际结果和覆盖范围；自动化结果不得冒称成员原始记录或人工体验评价。
- A 补测通过后，按实际覆盖范围解除“缺证据”阻塞。规则矛盾、关键业务定义缺失或功能尚未实现时，仍保留对应阻塞；契约/静态核对不等于业务运行通过。
- 复测使用独立临时库和明确标记的模拟数据，避免更改日常演示数据。业务阻塞仍统一记录在 [BLOCKERS](BLOCKERS.md)，勘误用编号交叉引用，不另建一套冲突的待办。
