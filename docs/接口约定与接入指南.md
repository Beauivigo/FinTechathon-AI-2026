# 接口约定与接入指南 v1.1

这是共用版 v1.1，替代此前已上传的 v1.0。机器可执行规则以 `shared/contracts.py` 的 `ACTIONS`、`RECORDS`、`ENUMS` 为准。使用 Python 3.10+，不需要安装第三方包。六个业务场景包含 22 个动作，另有 4 个公共查询动作。内部服务函数不是模型工具，详见[内部服务与开工验收](内部服务与开工验收.md)。

**开始接入时先看 `examples/contracts.json`。** 它包含所有 26 个动作的完整请求/响应，以及待确认、待强验证、结果未知样例；这些是假数据格式示范，不执行交易。运行 `python -X utf8 -m examples.module_examples --write` 可重新导出，测试会检查文件是否与代码同步。

人员职责按[新版分工](五人分工与实施计划.md)：所有代码由 A 实现，B—E 提供业务规则、数据和独立验收。下文用组件名称描述执行边界，避免把人员分工与安全边界混为一谈。此次调整不改变 v1.1 接口。

## 1. 谁调用谁

用户 → 对话/页面 → `adapt_request` → 权限执行网关 → 对应业务模块 → `adapt_result` → `result_text` → 用户。

第一个箭头可以来自 LLM；权限执行网关和真实业务返回不能由 LLM 代替。模型负责提出工具调用，服务端决定能否执行。`shared/policy.py` 只计算需要什么权限，不执行交易、不验证身份；`source` 只是展示标签，不能作为可信身份凭据。

| 边界 | 发送方 → 接收方 | 必须一致的内容 |
|---|---|---|
| 意图到工具 | 意图模块 → 执行网关/业务模块 | `action`、标准化 `params`；不把整段自然语言直接当作可执行命令 |
| 权限与执行 | 页面/业务模块 → 执行网关 | 确认绑定操作摘要；用户身份来自服务端会话；模型不得传 `confirmed=true` 自行授权 |
| 资金与业务 | 理财/商户模块 → 公共资金服务 | 金额用整数分；申赎/商户支付复用统一账本，不另建余额 |
| 数据与报告 | 账本查询 → 分析/理财/订阅模块 | 交易标识、日期、金额、方向、状态一致；分析只读取已确定的账本记录 |
| 结果到界面 | 业务模块 → 页面 | `status`、`error.code`、`data`、来源标记；待确认、已安排、结果未知均不等于成功 |
| 跨场景 | 工作流 → 各模块 | `step_id`、`depends_on`、每步独立请求；计划生成不代表整体获准执行 |

## 2. 统一词典

| 业务概念 | 标准字段/值 | 说明 |
|---|---|---|
| 接口版本 | `schema_version: "1.1"` | 不支持的版本直接拒绝 |
| 单次请求标识 | `request_id` | 一次调用一个；重试可以使用新的请求标识 |
| 一次完整流程 | `trace_id` | 跨模块共用，方便查日志 |
| 同一笔业务操作 | `idempotency_key` | 所有写操作必填；重试复用，修改业务内容必须重新确认并用新 key |
| 金额 | `amount_minor` | 人民币整数分，120.50 元 = 12050；禁止 float/bool/负数；v1 仅 CNY |
| 额度/统计金额 | `limit_minor` / `total_expense_minor` | 整数分，可以为零；具体交易金额必须大于零 |
| 赎回份额 | `units` | 正十进制字符串，最多 18 位整数、8 位小数，例如 `"12.5000"`；不是人民币金额 |
| 时间 | `execute_at` / `remind_at` | `YYYY-MM-DDTHH:MM:SS[.微秒]+HH:MM` 或结尾 `Z`；必须含秒和时区，例如 `2026-10-12T09:00:00+08:00` |
| 日期 | `start_date` / `end_date` / `deliver_on` | `YYYY-MM-DD`；账单范围两端包含，按上海日期解释 |
| 收款人 | `payee_id` | 已消歧后的内部 ID；姓名/手机号先解析，重名先澄清 |
| 权限 | `green` / `yellow` / `red` | 由服务端规则计算；不能让 LLM 决定 |
| 产品/用户风险等级 | `R1` / `R2` / `R3` / `R4` / `R5` | 与 green/yellow/red 操作权限是两套不同概念，不能混用 |
| 数据来源 | `sandbox` / `bank` / `gateway` | sandbox 文案显示【模拟】；gateway 不可声明业务成功 |

ID 使用 1—128 位 ASCII 字符串：以字母/数字开头，后续可包含字母、数字、`_ . : @ / -`；不接受空格、整数或中文姓名。中文姓名放在 `display_name` 等文字字段。普通文字字段最多 4096 字符。整数不超过 `2^53-1`，避免跨语言精度损失；请求/结果 JSON 最大 256 KiB、32 层、10000 个节点。银行卡号/身份证号等不能拿来当示例 ID。所有金额输出也遵守整数分约定，不能在某个模块返回元。

标准写请求示例：

```json
{
  "schema_version": "1.1",
  "request_id": "req_001",
  "trace_id": "trace_001",
  "idempotency_key": "operation_001",
  "action": "transfer.create",
  "params": {"account_id": "account_1", "payee_id": "payee_1", "amount_minor": 12050}
}
```

`user_id`、当日累计转账、权限等级、确认状态都不从上述业务参数读取。服务端根据登录身份解析用户，校验其账户/卡片/订阅等资源的归属，再执行。

### 3.1 列表内部结构也必须统一

以下未注明可选的字段均必填，不接受额外字段。每类结果列表最多 100 项；查询更多交易使用分页。

| 字段 | 每个元素的结构 | 附加校验 |
|---|---|---|
| shares | payee_id、amount_minor | 收款人必须与请求完全一致且无重复；总额等于请求金额；均分后最多相差 1 分，每人至少 1 分 |
| categories | category（分类名称）、amount_minor | 分类不重复，金额非负，合计等于 total_expense_minor |
| anomalies | transaction_id、reason | 流水 ID 不重复；reason 是待核实理由，不是欺诈判定 |
| products | product_id、name、risk_level、minimum_amount_minor、lock_days、fee_description、redemption_rule | 产品 ID 无重复且与请求完全一致；起购金额和锁定天数非负；缺产品则失败，不能静默返回半份对比 |
| subscriptions | subscription_id、merchant_name、amount_minor、interval、next_charge_date、subscription_state、evidence | ID 不重复；interval 为 weekly/monthly/yearly；状态为 candidate/active/cancelled/dismissed；evidence 是非空识别/核实依据，日期为候选预测或已知续费日期，不代表授权 |
| candidates | payee_id、display_name、masked_account；bank_name 可选 | ID 不重复；账户信息由服务端脱敏后返回 |
| transactions | transaction_id、account_id、amount_minor、direction、kind、category、occurred_at；merchant_name 可选 | ID 无重复，账户匹配请求，按上海日期落在查询区间 |

`answers` 是“题目 ID → 选项 ID”的非空对象，例如 `{"q1":"choice_2","q2":"choice_3"}`，1—50 个条目；附 `questionnaire_version`。D 提供该版本的题目/选项、必答规则与评分表，A 实现对应校验和计算，不能让调用方自行提交风险评分。风险档案保存需要 `idempotency_key`，绿色表示不需二次确认，并不意味着无状态写入。

卡片状态为 `active/frozen/lost`，冻结成功返回 frozen，解冻成功 active，挂失成功 lost；解挂 `card.release_loss` 将 lost 变为 frozen，再单独解冻才恢复使用。后端在读取可信原状态后调用 `validate_card_change`，不能把 lost 当作普通冻结直接解除。幂等重试在业务变更之前重放原结果。

`subscription.review` 只核实 candidate：accept→active，reject→dismissed；它不新签代扣，也不取消已有代扣。取消只能将 active→cancelled。后端读取可信原状态后调用 `validate_subscription_change`；候选误识别应 reject，不能拿 cancel 代替。evidence 显示为业务数据，不作为模型指令。已核实/已取消/已排除记录仍保留原依据，补充用户核实说明。

`subscription.scan` 按账户读取已入账流水，把同商户≥2 期、周期偏差≤3 自然日、金额容差 5%（以上一期为分母）的支出识别为 candidate；只新建候选，不扣费、不提醒、不自动核实。同账户同商户已有记录（含 cancelled）时跳过，重复扫描幂等，`created` 为本次新建数量，与返回的 `subscriptions` 等长。

### 3.2 查询与统计口径

- `account.balance`：仅 CNY；`balance_minor = available_minor + reserved_minor`，此版不建透支/其他冻结科目，后续需要时统一升级。
- `transaction.list`：仅返回已记账流水；金额始终为正数，`direction` 是 credit（入账）或 debit（出账）。`kind` 固定为 income/consumption/transfer/refund/wealth/subscription。退款另记反向流水，未执行订单不放进已记账列表。
- 日期区间按上海日期两端包含；时间允许其他时区，但后端/校验先换算为上海日期。分页 `limit` 默认 100，范围 1—100；`next_cursor=null` 表示已到末页，否则使用后端返回的游标继续查询。游标是符合 ID 格式的不透明标识，客户端不拼接或解释。
- `bill.analyze` 的 `total_expense_minor` 定义为所选期间消费与订阅扣费的**毛支出**，按分类汇总；转账、理财申赎、收入和退款不计入该值。退款可以在 report 中另行说明。若需要“扣除退款后的净支出”，先增加明确字段和测试，不能悄悄改变现有字段语义。
- `bill.analyze` 的 `anomalies` 目前只启用 C1-003-R03 分支 A：账户在查询区间内单笔支出（消费/订阅/转账/理财，方向 debit）≥5000.00 元时返回一条提示，`reason` 内含金额、阈值与规则编号；同一流水只出现一次，按 `transaction_id` 升序。只提示核实，不拦截、不改账；其余异常规则未启用，空列表不代表没有异常。
- `operation.get` 的外层 succeeded 仅表示“查到了记录”；真正的交易结果在 `operation_result.status`，仍可能 unknown。`result_text` 自动展示原操作状态，保留“结果待核实、暂勿重新提交”等提示。原请求中的 action 和幂等键必须匹配查询条件，来源不能混合模拟与银行。查不到返回 NOT_FOUND，不能据此断言原请求一定未执行；服务端需继续核实。

共享库检查能由请求和响应直接证明的一致性。余额是否真实、异常原因是否正确、产品适当性、查询归属、实际交易是否发生，仍由后端和业务测试保证。

## 4. 金额和字段适配代码怎么用

```python
from shared.adapters import adapt_request

request = adapt_request(
    "transfer.create",
    {"accountId": "account_1", "recipient_id": "payee_1", "amount_yuan": "120.50"},
    request_id="req_001", trace_id="trace_001", idempotency_key="operation_001",
)
# request["params"] == {"account_id": "account_1", "payee_id": "payee_1", "amount_minor": 12050}
```

支持少量明确别名（见 `FIELD_ALIASES`），进入业务模块后只用标准名。`amount` 因为无法判断元/分直接拒绝；同时传 `amount_yuan` 和 `amount_minor` 也拒绝，避免不同模块优先级不同。`12.50` 这样的 float 不接收，传 `"12.50"`。

不要将所有可能的中文/英文都塞进适配器。中文自然语言由意图模块识别；身份证明和确认凭据由执行网关处理，均由 A 实现。适配器只处理明确的数据结构。

## 5. 返回状态与统一表述

所有结果都带 `schema_version/request_id/trace_id/action/status/source/data`。`succeeded`、`scheduled` 的 data 按对应动作填写；其余状态的 data 必须为空对象。scheduled 携带登记编号与执行时间，不代表已经转账。

| status | 页面/对话表述 | 是否可以说业务完成 |
|---|---|---|
| awaiting_confirmation | 待用户确认 | 否 |
| awaiting_verification | 待强验证 | 否 |
| scheduled | 已安排，尚未执行 | 否，定时转账只是登记成功 |
| running | 执行中 | 否 |
| succeeded | 当前 action 已完成 | 只能按该 action 的语义，例如申购订单提交不等于份额到账 |
| unknown | 结果待核实，请查询原操作状态，暂勿重新提交 | 否；超时但可能已扣款时使用 |
| failed / blocked / cancelled | 执行失败 / 已阻止 / 已取消 | 否 |

```python
from shared import adapt_result, operation_digest, result_text

# 固定演示凭据；真实 challenge 由服务端产生并保存。
raw = {"status": "WAIT_CONFIRM", "next_action": {
    "challenge_id": "demo_challenge_1", "kind": "confirm",
    "operation_digest": operation_digest(request, principal_id="demo_user_1"),
    "expires_at": "2026-10-12T09:00:00+08:00",
}}
result = adapt_result(request, raw,
    status_map={"WAIT_CONFIRM": "awaiting_confirmation"}, source="gateway")
text = result_text(request, result)  # 待用户确认。
```

模块本身已返回标准 status 时可省略 `status_map`；旧后端状态由程序员显式配置映射，不能把 `accepted`、HTTP 200、`ok=true` 一概当成业务成功。`adapt_result` 用于受信任的本地模块边界，允许 `status/data/error/next_action` 以及可选的 schema_version/request_id/trace_id/action；后端若提供关联字段，必须匹配请求，适配器不会覆盖错误关联。完整网络响应请用 `loads_result`，不允许省略关联字段。

`source` 和 `status_map` 是开发者设置的可信适配配置，禁止从用户或 LLM 的参数取值。标签与字段校验不构成银行执行证明。目前没有真实银行 API 可以声称已适配。

失败、阻止和结果未知必须带 `error: {code, message}`；统一错误码见 `ERROR_CODES`。未知结果必须配 `RESULT_UNKNOWN`。前端不直接展示可能含敏感信息的后端 `error.message`，统一使用安全文案；详细原因脱敏后进入审计。

### 5.1 确认/强验证与业务参数分开

只有网关可以返回 awaiting_confirmation/awaiting_verification，且必须带 `next_action`：

| 字段 | 约定 |
|---|---|
| challenge_id | 服务端产生并保存的这次确认/验证任务 ID |
| kind | confirm 或 verify，必须与结果状态对应 |
| operation_digest | 64 位小写 SHA-256 摘要，绑定版本、用户、动作、参数及幂等键 |
| expires_at | 带时区的到期时间；当前库只验格式，执行网关必须校验过期 |
| methods | verify 必填，允许 sms_otp/face/u_key/demo_otp 的非空去重列表；confirm 不传此字段 |

客户端通过独立的授权通道提交 `schema_version/challenge_id/operation_digest/decision`，decision 为 approve/reject；强验证通过后可附 `proof_token`。`validate_authorization` 仅校验提交格式；执行网关从保存的 challenge 查验当前用户、摘要、所需方法、有效期、凭证真实性与是否已使用，决定放行与否。没有 proof_token 的 approve 不能满足强验证，客户端不能通过省略字段降级；拒绝时不传 token。

授权载荷不属于 `ACTIONS`，不开放给模型作为工具参数。methods 表示允许的验证方法，真实多因素组合的判断由验证服务实现；demo_otp 仅用于明确标记的比赛模拟。令牌、验证码不进入普通对话或审计日志。

`operation_digest` 会将等价时间转换为 UTC，将份额小数末尾零去掉后再计算；修改金额/收款人/地址等会改变摘要，单纯重试的新 request_id 不影响摘要。读取原操作时先按原请求查询，再由网关构造当前调用的返回关联字段，不能直接把旧 request_id 的响应塞给新请求。

### 5.2 状态更新检查

`validate_transition(request, previous, current)` 检查同一请求的新旧响应。完全相同的结果可重复读取；succeeded/failed/blocked/cancelled/scheduled 是当前调用的终态，不能被改写。unknown 可以在核实后变成 succeeded/scheduled/failed，不能直接变成 cancelled。待强验证不能降级为待普通确认。

一旦来源为 sandbox 或 bank，后续同一操作结果必须保持该来源，也不能退回 gateway 再切换。允许授权阶段 gateway→固定业务后端。网关必须按部署配置绑定后端来源，并在重新生成重试响应时保持该绑定；单次字段校验无法识别伪造的来源。

scheduled 是“登记定时转账”的终态，到期真实执行另发 `transfer.create`，使用新请求 ID、独立执行幂等键并关联原定时记录；每次触发重试复用该执行键。取消已登记计划走独立内部服务，不能把已完成的 schedule 请求改成 cancelled。模型工具暂不提供任务取消与商户退款动作。

v1.1 已在内部 `BankServices.cancel_task` 约定取消尚未领取的任务；它由可信界面的任务管理入口调用，校验当前用户与原任务归属，不作为模型工具。它不会修改原 schedule 请求回执。商户退款仍需独立业务支持；当前用人工接管处理。

状态更新检查不读取确认凭据，不能代替权限网关。待确认直接到成功的返回过程可以合法，但执行网关必须已经验证了本次授权并实际执行。

## 6. 权限与执行的共同边界

题目明确：绿色查询可自动执行；黄色先展示详情并确认；红色强验证。转账以**包含本次的当日累计**判断：≤1000 元黄色，>1000 元红色。题目将订阅查询/取消、虚拟卡申请列入黄色，将挂失/解挂、理财申购列入红色。其余未明确项采用团队保守约定：赎回、卡限额/冻结解冻、商户下单红色，预算预留/释放、AA 收款单黄色，可在评审后调整。

`required_gate(request, transfer_used_minor=90000)` 表示服务端已读到当天已付和并发预占总额 900 元，不能从用户 JSON 或模型中获取。查询日界按 Asia/Shanghai；定时转账实际执行时重新检查当日累计、余额和授权。

函数仅返回 `risk_level/required_action/reason`，不再返回容易混淆的业务 `status`。required_action 为 execute/confirm/verify；execute 表示规则上可执行，不能当作“已经成功”。计入累计时排除当前幂等操作自身的预占，避免重试时再累计一次；并发额度预占由执行网关在事务内处理。

A 后续实现执行网关的顺序（B 提供业务规则与安全复核）：

1. 从服务端会话确认身份，检查账户/资源归属和安全锁定。
2. 校验并标准化参数；按用户、action、idempotency_key 查已有操作。相同内容重放原结果，不同内容报 IDEMPOTENCY_CONFLICT。
3. 原子读取累计/预占、余额等可信状态，计算权限要求；按 `operation_digest` 绑定用户、金额、收款方等完整内容。
4. 黄色校验用户对上述详情的明确确认；红色在详情确认后校验有效强验证凭证。凭证必须绑定摘要、用户、有过期时间且防重放，不能只是前端布尔值；摘要自身也不是凭证。
5. 在事务中重新检查额度并预占/扣款，执行白名单工具；写幂等结果和审计。并发及重试不得重复扣款。
6. 状态不确定先查原流水，不重新发起；可确认未执行才返回 failed。连续失败/可疑行为触发锁定，交人工处理。

以上是 A 的后续实现清单，当前共享库没有实现这六步的执行安全性。不能因调用了 `required_gate()` 就声称系统已具备权限控制。

审计至少记录：trace_id、request_id、操作摘要、脱敏用户/资源标识、识别到的意图、采用的规则编号与权限结果、确认/验证记录引用、工具名称、执行状态、错误码、时间。记录可审计的结构化决策依据，不要求保存模型内部思考过程，也不保存验证码/完整卡号。

第一版只允许模型选择预先定义的工具，不执行模型随意生成的 Python、SQL 或 shell。题目中的受限运行环境仍需 A 在后续运行配置中落实和展示，B/C 记录实测证据，白名单本身不等于沙箱隔离。

## 7. 跨场景的接口边界

```json
[
  {"step_id":"reserve", "action":"budget.reserve", "depends_on":[], "description":"预留生日预算"},
  {"step_id":"flowers", "action":"merchant.order", "depends_on":["reserve"], "description":"生日两天前下单鲜花"},
  {"step_id":"cake", "action":"merchant.order", "depends_on":["reserve"], "description":"生日两天前下单蛋糕"}
]
```

`validate_plan` 检查未知动作、重复步骤、缺失依赖与循环依赖，最多 100 步。计划仅描述步骤，不能直接执行；A 必须补齐每步参数并通过 `adapt_request`，从可信前序结果取 reservation_id，执行网关校验预留余额是否足够以及消费与预留归属。每步使用单独幂等键，共享 trace_id。调度时间由执行器保存，`deliver_on` 是配送日期，不能混作下单时间。`delivery_address_id` 引用服务端已保存且归属当前用户的地址；不让模型凭空生成地址 ID。

转账等已完成操作不可随意“回滚”。步骤失败后停下依赖步骤，明确展示部分完成；尚未使用的预算可释放，商户订单取消/退款需要对应业务支持，否则人工接管。确认时解释哪些步骤、金额和时间被授权，不能把一次“好的”当成未来所有交易的长期授权。

## 9. A 如何实现，其他成员如何验收

1. B—E 对照 `examples/contracts.json` 提供业务规则和预期案例；A 找到对应 action，沿用输入输出结构，用业务代码计算 data，不复制固定结果冒充实现。
2. 模型/旧表单的参数经过 `adapt_request`；已经符合标准的完整网络 JSON 使用 `loads_request`。后者会拒绝重复键、NaN、畸形 JSON，而普通 `json.loads` 可能静默覆盖重复键。
3. 页面/工作流调用统一权限执行入口。网关检查身份/归属/授权后，调用模块；这些代码均由 A 维护。模块的输入只取经过校验的 params；任意业务处理函数都不能直接暴露成绕过网关的写接口。
4. 本地模块返回值经 `adapt_result` 校验；外部完整响应使用 `loads_result(request, text)`。展示使用 `result_text`，列表与图表从经过校验的 data 取值。
5. 校验失败会抛 `ContractError`（ValueError 子类）。入口请求错误按 INVALID_REQUEST 返回；后端结果不符按 UPSTREAM_ERROR 记录并阻止成功展示。如果后端写操作已发送、无法确定是否执行，返回 unknown/RESULT_UNKNOWN 并核查原操作，不能因为解析失败直接再次扣款。
6. A 编写正常/异常自动化测试，并运行全库测试后再合并；C 组织实测与回归，B/D/E 复核业务预期。GitHub 的 `.github/workflows/contracts.yml` 配置为 push/PR 时在 Python 3.10 和 3.12 运行这些检查。

A 编码时直接 `from shared import adapt_request, adapt_result, ContractError`；仅导入 shared 不安装包、不联网、不执行任何业务。工作目录使用仓库根目录。
