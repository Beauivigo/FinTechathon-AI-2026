1. 打开程序：首次显示欢迎与设置入口，推荐“创建本机账号并启用手机验证”；已有账号直接登录，已建号但未绑定则继续绑定。演示入口须明确标识，真实模式启用后不能因出错退回演示验证。

3. 日常业务：提出需求→核对对象、金额与用途→按原权限确认或输入手机码→看到可信业务结果。绿色查询、黄色确认、红色强验证的既有规则继续适用；不把每次点击都变成验证码步骤。

绑定流程：验证已登录身份→本机显示绑定二维码/密钥→手机验证器添加→输入当前码验证持有→正式启用。绑定信息仅当次本机展示；TOTP密钥加密保管，密码与验证码不落日志、不进入模型。采用经审查的成熟实现与官方测试向量，不自创算法；新增依赖先核验许可、版本和兼容性。

交易流程：显示服务端确定的对象、金额及动作→输入手机码→检查时间窗口、已使用记录、失败次数及会话→生成仅对本次交易有效的证明→原网关重新检查资源与权限并执行。验证码本身没有金额绑定能力，必须由服务端把验证结果绑定到当前交易；同一码的重放和并发消费均须原子拒绝。登录通过不等于批准所有付款。

丢手机、换手机、解绑与密码恢复不能走“清空配置即可继续付款”的旁路；使用预先安全保存的一次性恢复材料及受控重新绑定流程，恢复动作不直接授权交易。真实模式关闭演示凭据签发/接受，配置错误时拒绝执行，不能静默退回模拟验证。

**专项验收**：正确码、错误码、过期/未来码、容许时钟偏差边界、同码重放、并发使用、错用户、交易内容变化、失效登录会话、五次错误锁定、凭据泄漏检查、恢复与解绑。跨平台测试与Windows加密能力分开记，不把Windows私有能力假定为Linux CI已验证。

**需要用户的唯一现场配合**：在代码验收后，用手机扫码绑定并在本机验证页面完成一笔模拟红色业务。绑定密钥、二维码、动态码和恢复码不发给AI、不上传GitHub。用户手机验收前标记“实现已测，实际绑定待验收”。

参考：[RFC 6238](https://www.rfc-editor.org/rfc/rfc6238)、[OWASP交易授权建议](https://cheatsheetseries.owasp.org/cheatsheets/Transaction_Authorization_Cheat_Sheet.html)。这些是技术设计依据，不代表主办方已认可本项目实现。

### H4：独立后台进程

复用现有`Scheduler`、`MerchantScheduler`及提醒服务，在页面之外增加可单独启动/停止的工作进程，首版继续使用SQLite。后台只读取已保存的受控计划，不在到期时重新调用模型决定收款对象、金额或商品。

任务领取采用有时限的占用记录或等效的数据库互斥，配合稳定操作键；重复启动不能双重执行。进程崩溃后的领取恢复先查原交易，不换键盲重试。任务完成与通知入队要有一致性保证，通知重试不得重新触发付款。

页面增加后台运行状态、最后检查时间、待确认/待验证/失败/待核实列表。站内通知持久保存并区分已生成、已展示、已读；Windows桌面提醒不显示验证码或完整敏感交易信息，关闭桌面通知不影响待办恢复。

**专项验收**：页面关闭后到期、后台重启、同时两个工作进程、领取后退出、执行后退出、取消与派发竞争、超出既定迟到窗口、验证超时、通知失败重试、电脑恢复运行后的补查。后台没有登录用户在场时不得自动签发交易验证证明。

### H5：生日流程和资金边界

| 时间点 | 自动完成的事 | 需要用户完成的事 | 失败/不确定时 |

本轮默认交付为**自动调度＋必要的现场授权**。完全无人值守的未来付款、跨日预算授权或自动释放，需要另行确定授权范围、上限、有效期、撤销和变更规则，不能用一次TOTP/计划确认替代。此扩展不阻塞H0—H4；也不能因默认范围完成而宣称已实现无人工介入的生日采购。

## A：商户主链路

接口按以下结论落地：`merchant.order` 增加**可选** `card_id`（向后兼容），错误码优先复用现有 `INVALID_STATE`/`LIMIT_EXCEEDED`，`application.cancel` 本轮不动。C-07、E-11 不影响本轮商户链路。

1. **选卡**：仅在 active 卡中选；限额覆盖本笔；多张满足按 `card_id` 升序；显式传 `card_id` 时校验归属、状态、限额；无卡、全冻结/挂失、限额不足分别给出明确错误码。确认页展示将使用的卡。
2. **下单与消费**：`merchant.order` 在既有 reservation 上登记并原子提交订单、`consume_reserved`、流水、幂等回执与审计；部分消费后保持 `partially_consumed`；剩余订单取得可信未执行证明且阻止迟到提交后，才释放对应金额，结清后转 `closed`；全额消费结清。
3. **未知与恢复**：提交后回执丢失按原订单键查询，不猜余额、不换键、不自动释放；迟到提交与释放互斥；取消商户任务后按可信未执行证明释放。
4. **执行前复验**：确认期间卡状态/限额变化则拒绝并重新选卡，不沿用旧授权；越权、跨账户、过期授权均有拒绝路径。

**验收标准**：

| 项 | 通过条件 |
|---|---|
| 选卡 | 九种情形（无卡、全冻结、限额不足、唯一卡、多卡、显式卡、冻结卡、他人卡、确认期间变更）各返回唯一结果，`card_id` 升序确定 |
| 下单 | 订单、消费、流水、幂等回执、审计同事务提交；部分消费后仅释放已获可信未执行证明且已阻止迟到提交的剩余金额，`closed` 与 `released` 不混用 |
| 恢复 | 同键重放原结果；回执丢失按原键查到真实结果；查无记录不判未执行；迟到提交不产生二次扣款 |
| 权限 | 越权账户/卡、过期授权、状态不符全部拒绝且不留副作用 |
| 回归 | 新增用例 + 全量测试通过，0 失败/错误/跳过；日常演示库指纹不变；证据落 `docs/evidence/` |

不在本轮：生日链路、`scenario.plan` 运行时、订阅取消/提醒、六场景路由——留到下一轮。
