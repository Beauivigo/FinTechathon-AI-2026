## 3. 已替你选好的开工方式

| 决策 | 本方案采用 | 理由及后续边界 |
|---|---|---|
| 页面与语言 | 继续 Python + 现有 Streamlit | 第一轮代码继续使用 |
| 调用方式 | 同进程 `execute` / `authorize` | 现有接口已确定，暂不拆 HTTP 服务 |
| 持久化 | Python 标准库 `sqlite3`，一个本地数据库 | 适合本次单机模拟；账户、流水、幂等和授权共同存储 |
| 模型 | P0—P6 不需要模型密钥，继续离线转账解析 | 先验业务正确性；模型接入放步骤 6，不能用模型计算余额或判定授权 |
| 身份与验证 | 服务端固定模拟身份；明确标识 `demo_otp` | 用另一模拟身份做越权测试；不宣称真实登录、短信或人脸验证已实现 |
| 数据 | 本文给出稳定虚构 ID 与初始余额 | 不等 C 交数据；后续材料经校验导入，不无条件覆盖已有账本 |
| 开发节奏 | 每次只实现一个 P 批次，验收后继续 | 不给整个项目一次性生成大量未验证代码 |
| 版本管理 | 继续 main，按批次保存可核验提交 | 不创建开发分支；不强制覆盖历史，不把运行数据库或密钥提交到 GitHub |

SQLite 无需单独数据库服务，Python 已提供标准库接口，参见 [Python 官方说明](https://docs.python.org/3.12/library/sqlite3.html)。这是本项目的实施选择，不代表真实银行系统的部署设计。

### P2：统一记账和单笔转账业务

**建议文件：** 在 `bank/services.py` 实现资金服务，新增 `bank/transfer.py`；扩充 `tests/test_bank.py`。

1. 业务入口沿用 `handle(params, *, context)`；只接受网关提供的身份、已校验请求、内部服务和事务。
2. 本批实现 `post_funds` 的 debit/credit 及配对转账。reserve 等预算能力留步骤 7，未实现时明确拒绝，不能返回假成功；调度同理。
3. 付款账户必须归当前身份，收款账户必须由可信 payee_id 映射；收款方可以是其他用户，禁止任意账户充值。
4. 一个数据库事务同时完成：转账业务、两边余额、两条流水、两个子记账幂等记录、操作成功结果和业务审计。
5. 每个子记账有不同 `posting_key`，但关联同一转账；资金命令和回执分别通过既有校验。余额非负且 `balance = available + reserved`，所有金额为整数分，更新后和累计值也不得超出接口整数上限。
6. 在扣款后、收款后、保存结果前分别注入故障，证明未提交时全部回滚。通过后才允许网关开放写操作。

**完成标准：** 内部测试能把 200 元转给李明并正确对账；余额不足、非法归属和中途失败不留下半笔业务。本批测试不得绕过网关成为页面的正式调用方式。

### P3：持久化执行网关、确认和模拟验证

**建议文件：** 扩展 `bank/gateway.py`，授权实现先集中在该处；新增 `tests/test_gateway.py`。

1. `execute` 校验请求、身份、资源、幂等与权限；普通转账必须先返回待确认/待验证并持久化，尚不记账。
2. 幂等唯一范围为“身份 + 动作 + 幂等键”，绑定 `operation_digest`。同键同内容返回既有结果，同键改金额/对象拒绝。
3. `authorize` 从 challenge_id 找回保存的原请求，核验身份、摘要、时效、决定和所需验证方式；不接受客户端重新提交金额来替换原请求。
4. 普通确认不能通过红色强验证；模拟凭证由服务端生成并校验，绑定用户与挑战、有效期、一次性使用状态。持久化摘要及必要元数据，日志不得保存明文凭证。
5. 采用 10 分钟有效期。过期不执行；明确确认未执行后结束原操作。用户再次发起时使用新请求并重新确认，不能暗中续期。
6. 授权与资金执行在同一写事务内核对最新累计、余额和挑战状态，解决并发越界。具体原则见第 6 节。
7. 在事务内构造、校验并保存关联原请求的完整成功结果，提交成功后才能向页面返回 `source=sandbox` 的 succeeded。不能先提交资金再发现结果无法保存或不符合接口；已提交但响应丢失时，客户端显示结果待核实，不能改为失败。
8. 成功后的重复调用只能查询/重放同一结果，不能再次消费授权或记账；错误凭证、错用户不能覆盖已经成功的原操作。
9. 拒绝、过期、授权失败和记账结果均留审计；交易成功审计随事务提交，失败审计在确认回滚后独立保存。

**完成标准：** T03—T11、T13、T17—T18 中对应网关检查通过；日累计来自数据库，不再固定为 0。

### P4：原操作查询、异常与重启恢复

**建议文件：** 扩展网关查询及 `agent/controller.py`；扩充调用流程测试。

1. 所有写请求先有稳定操作键；异常后保留它，禁止为了“重试”换一个键再次扣款。
2. `operation.get` 返回保存的原请求和原结果。外层 succeeded 只表示查到记录，页面仍按内层结果显示业务状态。
3. 分开保存“客户端没有拿到回执”与“后端业务状态”。通信异常不能覆盖后端已持久化的待授权或成功记录。
4. 恢复时校验原请求/键/身份，再读取权威业务状态：仍待授权就展示原挑战；已成功就展示原流水；后端确为 unknown/running 就继续核实并阻止再次发起。
5. 不把客户端临时的 unknown 硬做成后端 `unknown → awaiting_confirmation` 状态转换；现有状态校验不允许这一转换。修改 controller 的观察状态与业务状态管理，并添加回执丢失测试。
6. 为刷新后的页面提供一个**受信任内部查询**，按当前身份列出近期操作的动作和幂等键，再经 `operation.get` 恢复。它不是新增公开模型动作，也不接受页面随意指定他人身份。
7. 查询返回 NOT_FOUND 时保留“待核实”提示，不能据此声称一定未扣款；继续核对原操作及账本。只有确有未执行证据才结束为失败。

**完成标准：** “确认卡已存但响应丢失”和“转账已提交但响应丢失”两种故障都可恢复；重启不重复转账，不自动确认旧挑战。

## 5. 接口交接清单：编码时逐条核对

| 交接位置 | 必须沿用 | 最容易出错的地方 |
|---|---|---|
| 中文 → 请求 | `adapt_request`；schema_version=1.1；程序生成 request_id、trace_id、幂等键 | 金额用整数分；不能让模型造身份、账户或收款人 ID |
| 页面 → 网关 | `execute(request, *, principal_id)` | principal_id 来自服务端模拟会话；资源查询不等于已授权 |
| 确认 → 网关 | `authorize(payload, *, principal_id)`；先 `validate_authorization` | payload 是挑战、摘要、决定、必要凭证；输出关联保存的原请求 |
| 网关 → 模块 | `handle(params, *, context)` | context/transaction 仅后端构造；页面不能调用内部记账能力 |
| 模块 → 资金服务 | `post_funds(transaction, command, *, principal_id)` | 子记账独立 posting_key；该函数不自行提交事务 |
| 网关 → 页面 | `adapt_result`、`validate_result`、`result_text` | pending 来源 gateway、data 为空；业务成功来源 sandbox，且必须已提交 |
| 重试 → 既有操作 | 查“身份+动作+幂等键”，核摘要 | 新 request_id 只改变本次响应关联，不产生新转账；保存的原请求不能被重试覆盖 |
| 重试后继续授权 | 先取回持久化原请求和当前挑战 | authorize 的回执按原请求校验，不能拿新重试的 request_id 去错误匹配 |
| 原操作 → 页面 | `operation.get` 的 `operation_request` / `operation_result` | 外层 succeeded 不是原交易 succeeded；终态不能回退或改写 |
| 余额/流水 → 展示 | `account.balance` / `transaction.list` | 所有者校验；上海日期闭区间；遍历 next_cursor，最后为 null |

仅实现本批需要的五个公开动作：`payee.resolve`、`account.balance`、`transaction.list`、`operation.get`、`transfer.create`，另加既有内部资源/授权入口。其余动作可以暂时明确返回能力未开放错误，不删除其共享定义，也不伪造可调用成功。

业务错误只用现有 ERROR_CODES。输入契约无效可抛 `ServiceError(INVALID_REQUEST, 安全文案)`；已接受请求用标准失败响应。无法确定写入结果时使用 `unknown / RESULT_UNKNOWN`，不得用泛化“系统错误”诱导重新付款。

## 6. 三个必须在动手前讲清的技术细节

### 6.1 数据库事务与并发累计

首版采用短写事务串行化：在读最终余额、累计和挑战状态之前取得 SQLite 写事务；权限重算、双边记账、挑战消费和成功结果一起提交。不在等待用户确认期间持有数据库锁。

实现可使用显式 `BEGIN IMMEDIATE`，连接按调用管理，读写参数使用 SQL 占位符；兼容 Python 3.10/3.12，不依赖仅 3.12 存在的连接参数。锁忙时有界等待，不能随意报告扣款失败再换键。SQLite 同时只允许一个写事务，IMMEDIATE 也可能遇到 busy，参见 [SQLite 官方事务说明](https://www.sqlite.org/lang_transaction.html)。具体提交/回滚方式须在实现时统一，禁止一半显式事务、一半依赖隐式提交。

本方案暂定按**用户在上海当日的全部成功对外转账支出**汇总，不按浏览器会话或某一张页面卡片计数；执行当日重新计算，重放同一业务不重复累计。该汇总范围交 B 复核，1000 元阈值及“含本次”不能降低。

待用户确认的请求暂不预占日额度。首版所有最终授权与记账均在同一短写事务完成，所以不会有另一笔已放行但尚未入账的转账穿过累计检查；后来的写事务必须看到前一笔提交。以后引入异步放行时，必须统计并发额度预占且扣除本操作自己的重复占额。

例：当日已转 800 元，同时准备两笔 200 元。第一笔确认后累计 1000 元；第二笔执行前重查，必须升级为待强验证，旧普通确认不能直接放行。升级时保存新挑战并废止旧挑战，金额与收款人不变。红色要求不因累计后来变化自动降级。

### 6.2 授权、持久化和崩溃

- 等待用户操作时，原请求、当前结果和挑战已存库；没有扣款。
- 最终执行前重新校验归属、金额、余额、累计、挑战及验证凭证。余额或权限在等待期间变化，不能照旧页面盲目执行。
- 挑战消费与记账在同一事务：回滚时不留下“凭证被消耗但业务无记录”的半状态；提交后重试只能读原结果。
- 初始确认的回执丢失：恢复后仍显示同一待确认卡；不能新建第二笔。成功回执丢失：恢复后显示原成功流水；不能再扣一次。
- 暂定同一挑战连续 5 次无效模拟验证后锁定该挑战，原业务为 `blocked / SAFETY_LOCKED` 并留审计，随后需重新发起并确认。仅统计已识别的所属用户的验证失败，错用户不能借此锁定他人挑战。该阈值供 B 复核，不作为完整账户风控的替代。

### 6.3 对账和资料替换

对账至少检查：付款减少额=收款增加额；两条流水金额相等、方向相反、同一业务关联；一笔业务一个成功结果；账户余额=开账余额+全部已提交入账−全部已提交出账。

C 后续的历史流水需与开账余额共同校验，不能在已更新余额上再次重放一遍账单造成重复入账。D/E 材料用稳定 ID、版本和字段校验导入；更新目录不改写旧订单/旧交易事实。导入失败整体拒绝并指出数据行，不静默“修好”金额或关联 ID。
