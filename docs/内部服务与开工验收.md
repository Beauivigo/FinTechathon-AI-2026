# 内部服务与开工验收 v1.1

本文约定程序模块间的交接边界。按[新版分工](五人分工与实施计划.md)，全部代码由 A 编写，B—E 提供规则、数据及独立验收；人员集中不取消网关、事务和授权边界。公开动作看[接口指南](接口约定与接入指南.md)，内部数据完整例子看[internal_contracts.json](../examples/internal_contracts.json)，可执行校验与函数签名看[shared/services.py](../shared/services.py)。这些是协议和样例，不是已经运行的银行、网关或调度器。

## 1. 固定的开发边界

- 一个 Python 项目，先用模拟银行、模拟产品和模拟商户；所有实际业务由后端计算，不复制样例结果冒充执行。
- A 维护对话/界面、各业务模块、身份、账本、执行网关、内部服务、运行隔离和自动化测试。B 提供资金/权限规则与安全复核；C 提供数据/账单口径及测试记录；D 提供理财规则与材料；E 提供卡片/订阅规则、文案及演示素材。
- 模型只能提出 ACTIONS 中的请求；`get_context/post_funds/register_task/get_task/cancel_task` 是受信任服务端能力，不能注册到模型工具表。自然语言、模型输出不能创建 principal_id、transaction 或任意 Python 调用。
- 身份来自服务端登录会话，资源 ID 来自该身份的可信查询。任何查询/操作都由执行网关再查归属和实时状态；通过 JSON 校验不代表有权限。
- 第一版不承诺无人值守资金交易。定时转账、生日采购到期后重新进入权限网关；缺少本次有效确认/强验证就等待用户，不扣款、不反复创建新任务。
- 当前未实现真实短信、人脸或 U 盾。演示使用清楚标记的 demo_otp；赛事是否接受模拟强验证需对照后续正式说明确认，不能将接口存在写成真实验证已完成。

## 2. 页面/工作流调用的两个网关入口

采用同进程 Python 函数，首版不要求 HTTP 服务。以下入口由 A 实现，供页面/工作流调用；B 复核资金及授权规则：

```text
execute(request: dict, *, principal_id: str) -> dict
authorize(payload: dict, *, principal_id: str) -> dict
```

`execute` 输入是 `validate_request` 通过的完整请求，输出必须通过 `validate_result(request, result)`。执行网关先处理资源归属、幂等和权限，再调用模块。业务模块约定 `handle(params: dict, *, context: dict) -> dict`：params 是已校验的参数；context 仅由网关构造，包含 principal_id、request（完整原请求）、services（BankServices 实例）、transaction（网关的事务对象；纯读为 None）。context 不是 JSON，不接受客户端/模型提供。模块返回 `status/data`，需要时带 `error`；网关用固定部署来源调用 adapt_result，页面用 result_text 展示。

`authorize` 输入通过 `validate_authorization`；执行网关按 challenge_id 找回保存的原请求，核对当前身份、摘要、时效、所需验证方法、凭证真实性和是否已使用。通过后继续原操作，输出与**保存的原请求**关联的完整响应；调用方持有该原请求来校验响应，不能把授权 payload 当业务请求。拒绝则返回原请求的 cancelled 结果。强验证缺少有效 proof_token 时不能放行。

请求格式已经损坏时，不能把无效请求硬塞给 adapt_result：在入口捕获 ContractError，返回传输层错误（例如 HTTP 400，或同进程 ServiceError(INVALID_REQUEST, 安全文案)），不伪造 request_id 或成功结构。已接受的有效请求发生业务错误时，才构造对应的标准结果。

ServiceError.code 使用现有 ERROR_CODES。写操作是否发生不确定时必须是 RESULT_UNKNOWN，对外 unknown；只有确认没执行才报告 failed。原始 error.message 不直接显示给用户。网关及模块之间的事务必须覆盖订单/状态、账本、幂等结果和审计，不能先扣款再单独保存订单。

## 3. 可信资源快照：get_context

`services.get_context(principal_id=当前会话身份) -> dict`，返回后调用 validate_context。

快照构造、导入、归属校验和查询均由 A 编码；下表第三列只指资料与业务复核负责人。

| 数组 | 每条必填字段 | 资料/业务复核 |
|---|---|---|
| accounts | account_id、display_name | B 定规则，C 提供模拟数据 |
| products | product_id、name、risk_level、minimum_amount_minor、lock_days、fee_description、redemption_rule | D |
| holdings | holding_id、account_id、product_id、units | D 提供持仓规则/样例，B 复核资金与归属规则 |
| cards | card_id、account_id、card_state、limit_minor | E |
| items | item_id、name、price_minor | E 提供目录，B 复核预算/价格规则 |
| addresses | delivery_address_id、label | E 提供虚构展示标签，B 复核归属规则；label 不含完整地址 |
| questionnaires | questionnaire_version、questions | D |

顶层还有 schema_version 和 source（sandbox 或 bank）。所有数组可以为空，单类最多 100 条，适用于小规模比赛模拟；达到上限须升级为分页接口，不能静默截断。卡片/持仓关联账户必须在快照中，持仓关联产品必须包含；已下架但仍有持仓的产品仍须保留其事实记录，后端另行拒绝新增申购。零份额持仓不列入此快照。

问卷 questions 为 1—50 项，每项 question_id、text、choices；choices 为 2—20 项，每项 choice_id、text，同层 ID 不重复。D 提供问卷与评分规则，A 在服务端根据该版本校验完整性、合法选项并计算风险评分，模型不能自行创造题目/答案 ID。

此快照用于选择对象，不作为执行凭据。申购/下单仍查最新风险、价格、状态、地址归属；余额从 account.balance 读取，订阅仍走黄色 subscription.list，不能借快照绕过确认。完整地址保存在服务端，由 delivery_address_id 引用。

账单模块由 A 按 C 的统计口径使用 transaction.list 逐页汇总后提供图表，先不往 bill.analyze 自加 trend 字段；统计口径仍遵守接口指南。产品对比理由由 A 实现的可信模块按产品事实和风险档案生成，D 提供解释规则及核对样例，不在固定 products 记录内随意加字段，也不编造收益率。若后续需要独立传输图表序列/推荐理由，统一升级契约及测试。

## 4. 公共资金交接：post_funds

`services.post_funds(transaction, command, principal_id=当前身份) -> receipt`。command 调用 validate_funds_command，回执调用 validate_funds_receipt。transaction 必须是执行网关开启的有效事务；接口本身不创建或提交事务。

command 必填 schema_version、posting_key、trace_id、account_id、reference_id、effect、amount_minor、kind；预留相关动作另必填 reservation_id，普通收支禁止该字段。所有金额是正整数分；reference_id 指向订单/原业务记录，posting_key 是**记账子动作**幂等键，不能直接给每个子动作复用同一业务幂等键。

| effect | 余额变化 | 可用变化 | 预留变化 | 用途 |
|---|---:|---:|---:|---|
| debit | −金额 | −金额 | 0 | 普通付款/申购扣款 |
| credit | +金额 | +金额 | 0 | 后端核实后的入账/赎回到账 |
| reserve | 0 | −金额 | +金额 | 预算预留 |
| consume_reserved | −金额 | 0 | −金额 | 使用指定预算付款 |
| release_reserved | 0 | +金额 | −金额 | 释放指定预算的未用部分 |

始终保持 balance_minor = available_minor + reserved_minor。执行网关在同一事务检查金额、账户归属、指定预留的归属和剩余额度；不得以其他预留金额填补不足。reserve 的 reservation_id 由服务端生成；重复调用同 posting_key、同内容返回原回执，不同内容报 IDEMPOTENCY_CONFLICT。不同预留使用不同 ID。

receipt 必填 posting_key、entry_id、account_id、reference_id、effect、amount_minor；除 entry_id 外与 command 对应字段一致。回执表示事务内已记账，**外层事务提交前不得向用户报成功**。只有已提交 debit/credit/consume_reserved 生成相应收支流水，reserve/release_reserved 只记预留及审计，不重复计入消费。kind 使用共享 transaction_kind；C 的账单仍只统计确定的消费和订阅支出。

D 提供申赎订单规则，B 复核资金口径，A 编写业务计算和资金执行代码。赎回“订单已提交”时不能自动按任意金额入账，份额确认/净值/到账规则由可信理财模块计算后再交公共资金服务。内部 credit 绝不能暴露给模型。跨账户转账的各子记账以及双方账本更新必须在一个事务内；中途失败整体回滚。

转账付款账户必须归当前用户；收款账户由服务端从已授权请求的 payee_id 可信解析，可以属于其他用户。该账户的 credit 仅允许作为这笔已核验转账的配对子记账，不能允许调用方任意指定外部账户充值，也不能误把所有收款账户都限制为付款用户本人所有。

## 5. 通用调度：register_task / get_task / cancel_task

三个入口签名见 BankServices。register_task(transaction, spec, principal_id=...) 返回 state=scheduled 的任务；get_task(task_id, principal_id=...) 查询；cancel_task(transaction, task_id, principal_id=...) 只取消尚未被领取的 scheduled 任务，返回 cancelled。对同一已取消任务可重复查询/取消；running/dispatched/unknown 不得伪装成已取消，返回 INVALID_STATE 并核实原执行结果。

spec 必填 schema_version、task_key、trace_id、run_at、kind、origin_action、origin_idempotency_key、payload。run_at 带时区；登记时服务端检查为合理未来时间，调度器使用可注入时钟做测试，不直接修改系统时间。

内部协议首版只在同进程传字典；如果以后改为网络调用，先用 shared.adapters.strict_json_loads 解析，再调用对应校验器，防止重复 JSON 字段被静默覆盖。

| kind / payload | origin_action | 到期行为 |
|---|---|---|
| execute_request / 完整 transfer.create 请求 | transfer.schedule | 重新走 execute；校验当天累计、余额、归属与本次授权 |
| execute_request / 完整 merchant.order 请求 | budget.reserve | 根据已保存且经用户确认的生日步骤，重新走 execute；核实预算、价格及收货信息 |
| notify_subscription / {subscription_id} | subscription.remind | 内部提醒发送，按 task_key 去重；先复查订阅仍 active |

origin_idempotency_key 关联已保存的原操作，不能由模型任意声称。任务与执行请求共用 trace_id；到期执行使用独立 idempotency_key，所有重试复用它。task_key 按用户唯一、同内容重放、不同内容冲突；多个生日步骤分别用稳定 task_key 与执行 key，不要因重试生成新 key。

生日任务必须关联所属预算和已确认计划，逐步参数由可信前序结果及用户确认内容构建。执行网关必须核对原操作已登记/已预留、金额/收款人/预算/日期与保存记录一致；仅通过 validate_task_spec 不能证明这些关系。商户任务只能在已知 reservation_id 后登记，run_at 是下单时间，deliver_on 是配送日期。因重启/延迟发现配送日期已过，交用户重新确认，不能静默补单。

任务结构是 task_id、state、spec，调用 validate_task；更新调用 validate_task_transition：

- scheduled → running 或 cancelled；领取/取消必须以数据库原子条件更新，避免同时成功。
- running → dispatched、failed 或 unknown。
- unknown → dispatched 或 failed，先核查稳定执行键，不直接取消或重新发起新业务。
- dispatched/failed/cancelled 是终态，不能改写任务 ID 或 spec。

**dispatched 只代表任务已交给执行网关/提醒服务，不代表扣款成功、强验证完成或通知已被阅读。** 资金任务在网关待确认/待验证时，调度任务可以已 dispatched；页面/工作流查询 payload 的原写操作（operation.get）取得真实业务状态，再展示确认卡片，之后由 authorize 继续。提醒到达状态由后续通知后端提供，首版只演示内部通知。

领取、派发、登记操作与恢复需要 A 实现持久化。崩溃后检查原操作键，恢复同一任务；不能把数据库仍 running 当作可无条件重新扣款的依据。用户中断整个计划时，取消未领取任务、阻止网关尚未执行的步骤、核实已派发操作；仅在确认没有执行中/结果未知的预算消费后，释放剩余预算。已下单订单不能靠改任务状态“回滚”，转人工接管。

## 6. 交付顺序与验收责任

阶段总表以[五人分工与实施计划](五人分工与实施计划.md)为准。A 原第一轮只验页面、统一调用示例和缺参追问，允许明确标识的测试替身；不把下面的实际模拟扣款要求倒加到已完成的第一轮。

| 顺序 | A 编码交付 | B—E 同期交付 | 通过条件 |
|---|---|---|---|
| 第一轮 | 输入页面、一次统一调用、缺参追问；已有成果统一在 main | B 账户/权限规则；C 小账本/手算；D 产品/问卷；E 卡/订阅规则和确认草稿 | A 三项原验收有效；其他成员按实际资料核验，接口统一为 1.1 |
| 第二轮 2.1 | 持久化资源/账本、单笔转账、权限入口、幂等与审计 | B/C 提规则与手算，实际复核资金和权限 | 输入→确认/验证→模拟记账→流水/原操作查询可对账，重复不重复扣款 |
| 第二轮 2.2—2.3 | 其他业务最小模块、意图路由和生日计划，复用内部服务 | C/D/E 给规则、数据、预期并独立验收；B 复核资金规则 | 模块分别可调用；未接资金/调度处明确标测试替身或未集成；计划不冒充执行 |
| 第三轮 | 定时/AA、统一资金/调度、预算/商户、生日执行、中断/恢复与运行隔离 | B 安全/资金验收；C 组织回归；D/E 核业务及展示 | 六场景贯通，下表 G01—G15 全部实测通过，再增加功能 |

A 负责全部技术实现及修复；B/C 用越权、注入等用例或 A 提供的测试入口核验证据。D/E 复核自己的业务结果。文档和演示区分“契约已校验”“模拟业务已实现”“真实服务未接入”。main 包含共享底座与第一轮页面测试替身，仍不等于完整资金/安全集成。

## 8. 共享及迁移

1. 全员同步同一 main 提交，在仓库根目录用 Python 3.10+ 运行 unittest 与 demo；新接口都在 shared 导出。
2. 改动公共协议时同步代码、两组JSON样例、文档和测试；不兼容改动升级 schema_version。
3. 1.0 的请求/摘要/待确认记录不能直接当1.1使用。尚未执行的旧任务应暂停并重新确认；已执行历史保留原版本归档，不直接改写数据以绕过校验。
4. 样例中的金额、日期和回执都是静态格式示范，不是一套连续发生的真实交易。实际运行时用后端时间和数据，切勿复用样例 challenge/proof 或将过期日期登记进真实调度器。
