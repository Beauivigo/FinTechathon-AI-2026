## 1. 直接运行

在项目根目录执行；使用已有 `.venv`，本批未增加依赖：

```powershell
.\.venv\Scripts\python.exe -B -X utf8 -m bank.seed init
.\.venv\Scripts\python.exe -B -X utf8 -m bank.seed show
```

第一条首次创建并导入 `runtime/sandbox.sqlite3`，再次执行只提示“原数据保持不变”。第二条使用固定服务端模拟身份 demo_user_a，经网关查询 A 的余额，初始为 200000 分（2000 元），可用 200000 分、预留 0。收款账户初始均为 0。当前没有实际转账，因此初始流水和原操作为空。

种子包含 4 个用户、4 个账户和 A 的 3 条收款人映射：李明、小王一、小王二。两个小王都显示为“小王”，以银行和尾号区分，不自动选择。手机号查询使用全零开头的虚构测试值 `00000000001`—`00000000003`，仅用于测试，不是真实联系方式；返回结果不泄露手机号或内部收款账户 ID。

**只有需要清空演示数据时才运行：**

```powershell
.\.venv\Scripts\python.exe -B -X utf8 -m bank.seed reset --confirm-reset
```

该命令清空固定演示库的账户运行状态、流水、操作、挑战、审计和分页游标，然后重新导入种子。没有确认参数会拒绝；不接受任意路径；拒绝链接路径、硬链接、其他应用数据库和不支持的数据库版本。重置在单个事务内完成，中途失败保留原数据。它不是取消交易或核实未知结果的方式。

运行数据整个 `runtime/` 已加入 Git 忽略规则，包括 SQLite 的日志和附属文件。需要提交的是代码、种子定义和文档，不是运行中的数据库。

## 2. 接入接口

下面是同进程 Python 调用示例，适合后续 A 的控制器接入。principal_id 来自服务端模拟会话，不能从模型或用户请求参数直接接收：

```python
from bank.gateway import BankGateway
from bank.seed import demo_path
from bank.store import Store
from shared import adapt_request, validate_result

gateway = BankGateway(Store(demo_path()))  # 先执行 bank.seed init
context = gateway.get_context(principal_id="demo_user_a")
request = adapt_request(
    "payee.resolve",
    {"query": "小王", "match_type": "name"},
    request_id="req_example",
    trace_id="trace_example",
)
result = validate_result(
    request, gateway.execute(request, principal_id="demo_user_a")
)
print(result)
```

| 入口 | P1 行为 |
|---|---|
| get_context | 返回当前身份的账户，其他业务数组为空；不把余额塞入账户快照 |
| payee.resolve | 按当前身份的收款人映射精确匹配姓名/测试手机号；同名返回多个候选 |
| account.balance | 校验付款账户归属，返回余额、可用、预留、CNY |
| transaction.list | 校验归属、上海日期闭区间和分页游标；默认每页 100 条，最多 100 条 |
| operation.get | 仅在当前身份下查原动作+幂等键；返回保存的原请求/结果，校验摘要与关联 |
| 其他动作与 authorize | 明确拒绝，P1 不生成授权挑战、不扣款、不返回假成功 |

原操作没找到返回 NOT_FOUND，不能解释为已证明从未扣款。查到原操作时，外层 succeeded 仅表示查询成功，业务状态看内层 operation_result。原操作查询的 pending/succeeded/failed 测试使用专门夹具，不代表已经实现真实模拟转账。

## 3. 存储与分页约束

- 数据库 `application_id` 标识本项目，`user_version=1` 是存储结构版本，与公开 JSON 接口 v1.1 分开；不自动覆盖未知版本或其他应用文件。
- accounts 保存开账、余额、可用和预留；数据库检查非负、安全整数上限和余额等式。开账不伪装成消费流水。
- operations 以“用户+动作+幂等键”唯一，保存原请求、结果和摘要；transfers、ledger_entries、challenges、audit_events 已有存储结构，业务写入留后续批次。
- 本轮 SandboxServices 只实现资源/查询，不声称已完整实现 BankServices 的资金和调度协议。
- 流水时间由 `utc_timestamp` 规范化为 UTC 六位微秒字符串。上海日期转换为完整精度的 UTC 起止范围，避免毫秒舍入把月底最后一微秒分到次月。
- 第一页保存已提交记录的序号上限；后续页按“时间+唯一流水 ID”继续，并排除之后插入的记录，即使新记录的业务日期较早也不会混进旧快照。
- 游标是数据库保存的不透明随机 ID，绑定用户、账户、起止日期；重启可继续，改用户/账户/日期或伪造游标会拒绝。每次先重新检查账户归属。
- 默认每页 100 条，最后一页 next_cursor 为 null。同一游标重查会返回相同记录；新游标 ID 不承诺与上一次完全一致。
- 分页依赖已提交财务流水只追加、不修改/删除旧行；P2 资金服务必须继续遵守。管理员重置会清除旧游标；手工编辑数据库不属于支持的业务操作。
- 当前单机小规模版本使用短写事务保存分页游标，暂未实现游标过期清理；不适用于无限量公网查询。

数据初始化、查询和重置均不从网页重载自动触发。数据库连接按调用关闭，异常事务回滚；测试使用临时库，不操作日常演示库。
