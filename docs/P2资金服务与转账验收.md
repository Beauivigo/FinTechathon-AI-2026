## 2. 内部接口与事务边界

| 代码 | 本批职责 |
|---|---|
| `bank/store.py` | 有效写事务登记、局部回滚保存点、P1→P2 存储升级 |
| `bank/services.py` | 为可信转账生成内部上下文；post_funds 的配对 debit/credit、子记账去重 |
| `bank/transfer.py` | handle(params, *, context)，保存转账、双边记账、原结果和成功审计 |
| `bank/seed.py` | 升级后保留数据初始化；重置时同时清理资金回执 |
| `tests/test_funds.py` | 22 项资金、事务、迁移及故障注入测试 |

`post_funds(transaction, command, *, principal_id)` 沿用既有共享协议。命令与回执经 shared 校验；所有金额为整数分。普通扣款同时减少 balance 和 available，reserved 不变；入账反向增加，始终保留余额等式和安全整数上限。

内部 transaction 是当前服务实例为一个有效写事务创建的临时令牌，绑定用户、完整请求和两条准确的记账命令。外部连接、只读连接、伪造对象、其他实例或已结束的令牌均不能记账。它是同进程程序边界，不是登录凭证，也不代表已经实现任意 Python 执行隔离。

付款账户必须归当前用户；收款账户从该用户的 payee_id 映射取得，可以属于另一个用户。credit 必须与本笔已记账的 debit 配对；不能改金额、账户、业务编号或追踪编号来任意充值。首版拒绝付款与收款为同一账户的请求，该业务选择交 B 后续复核。

一笔成功操作在同一个外层事务中保存：

1. 转账业务记录。
2. 付款余额、付款流水和 debit 幂等回执。
3. 收款余额、收款流水和 credit 幂等回执。
4. 已校验且关联原请求的完整成功结果。
5. 与该请求 trace_id 关联的成功审计。

模块返回的 succeeded 是**事务内业务结果**。外层提交完成前，不得展示给用户；独立读连接此时仍看到提交前的余额和记录。

转账作用域有保存点，单次 post_funds 也有保存点：即使调用者捕获错误并继续使用外层事务，也不会留下半次扣款。仅做一边记账而不完整保存业务结果，会在退出作用域时回滚。post_funds 和 handle 都不自行提交外层事务。

## 3. 重复请求与错误结果

- 同一用户、动作和幂等键绑定 operation_digest；同键同内容返回原结果，同键改金额、收款人或备注报 IDEMPOTENCY_CONFLICT。
- 新重试的 request_id/trace_id 不覆盖持久化原请求；对外重放时按当前请求关联字段构造响应，保存的业务事实保持不变。
- 同一 posting_key、同一命令重复调用返回原回执；同键更改任一命令字段拒绝，不再次改变余额。
- 已保存的成功、失败、未知等非待授权状态只读取重放，不重新扣款。unknown 的结果核实仍由后续 P4 完成。
- 扣款读 available，不能动用已预留金额；付款不足、收款余额溢出、日累计超过 JSON 安全整数范围均拒绝。
- 此处的日累计检查仅防止整数范围溢出，**不代替 1000 元权限分级**。
- 失败通过异常交给可信调用者，已执行子动作回滚；失败/拒绝授权的业务结果和安全审计由 P3 接手，本批只实现随成功交易原子提交的审计。
- reserve、consume_reserved、release_reserved 尚未实现，明确拒绝；调度能力也未开放。

## 4. 旧数据库保留数据升级

数据库存储版本从 1 升到 2，只增加 `fund_postings` 表并更新数据库版本标记；公开 JSON 接口保持 v1.1。执行原初始化命令即可升级，不重建种子余额：

```powershell
.\.venv\Scripts\python.exe -B -X utf8 -m bank.seed init
.\.venv\Scripts\python.exe -B -X utf8 -m bank.seed show
```

迁移和版本号在同一事务内提交；结构不完整、外来数据库、未知版本或新表冲突会拒绝/回滚，不自动删除旧数据。重复初始化保持余额和历史。本次本地演示库已从存储版本 1 升至 2，升级前后账户、转账数及流水数一致，A 仍为 2000 元，其他账户仍为 0。

固定演示库重置也已适配资金回执表；仍需显式 `reset --confirm-reset`，不会随页面刷新执行。

## 6. 交给 P3 的具体要求

P3 网关必须先校验身份、请求、幂等和确认/验证，再在**同一个有效写事务**中重新计算当日累计、余额和挑战状态，创建 transfer_context 并调用 handle，消费挑战，然后提交。不能先提交资金再单独更新挑战；不能把 transfer_context 注册为模型工具或页面调用入口。

重放已有结果时保留原业务来源，正确关联本次请求；authorize 返回仍按保存的原请求校验。已确定的业务终态不能改写。写入结果不确定时核实原操作，不换新键扣第二次。

P2 的内部上下文不验证用户是否真的点过确认，也不检查验证码，因此不能直接接入公开 execute；当前代码仍明确拒绝公开写入与 authorize。下一批完成这些要求后，再逐步开放单笔转账。
