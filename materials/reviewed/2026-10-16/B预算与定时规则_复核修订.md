## 1. 预算预留：数据模型（给 A 的落地要求）

### 1.1 预留记录必须保存

| 字段 | 含义 |
|---|---|
| `reservation_id` | 服务端生成，`budget.reserve` 返回；不同预留不同 ID |
| `principal_id` / `account_id` | 归属用户与付款账户；执行时再查归属，不信任入参快照 |
| `amount_minor` | 预留总额（正整数分） |
| `remaining_reserved_minor` | 仍被预留的金额，初始 = `amount_minor`，随 consume/release 递减 |
| `purpose` | 用途（如“生日”）；仅展示，不参与资金判定 |
| `state` | `active` / `partially_consumed` / `released` / `frozen` / `closed`（见 1.3） |
| 关联订单 | 每个 `order_id`：计划金额、当前状态（`planned/running/succeeded/failed/unknown`）、对应 consume 金额、posting_key |

### 1.2 五种资金 effect（契约已固定，复核确认）

| effect | balance | available | reserved | 是否产生收支流水 |
|---|---:|---:|---:|---|
| `reserve` | 0 | −金额 | +金额 | 否，只记预留与审计 |
| `consume_reserved` | −金额 | 0 | −金额 | 是，消费落账 |
| `release_reserved` | 0 | +金额 | −金额 | 否，只记预留与审计 |
| `debit` | −金额 | −金额 | 0 | 是 |
| `credit` | +金额 | +金额 | 0 | 是 |

- `reserve` / `consume_reserved` / `release_reserved` 必须带 `reservation_id`；普通收支禁止携带。
- `consume_reserved` / `release_reserved` 的金额只能从**该预留的剩余预留额**里出；不足直接拒绝，不得以其他预留或 `available` 填补（V1.1 已定“超预留消费”分支）。
- `release_reserved` 的实际释放金额由**服务端按订单核实结果计算**，用户不能自报金额：公开 `budget.release(reservation_id)` 只传预留 ID，服务端释放“可安全释放的全部剩余”，公开成功data按v1.1仅返回 `reservation_id`；释放金额只作内部审计值，不新增公开字段。若无安全可释放余额，则内部释放金额为0，禁止发送金额为0的资金指令，预留保持 `frozen`。

### 1.3 预留状态机

> 待B确认：以下保留原稿以定位冲突，不作为通过预期。unknown不能说明事务未提交；已提交订单和扣款不得在核实后重复consume。请分别给已提交/未提交分支的余额与剩余预留。

```
active ──consume 部分──> partially_consumed ──consume 完且剩余释放──> closed
  │                         │
  │ release 全额            │ release 可释放剩余（仍有 unknown 绑定则留 frozen）
  v                         v
released（=closed）       frozen（存在未核实订单，剩余=被绑定金额）
                             └─核实后：succeeded→consume 落账→closed；failed→release→closed
```

- `active`：已预留，无任何订单进入执行。
- `partially_consumed`：已有 succeeded 订单 consume，尚有剩余预留。
- `frozen`：存在 running/unknown 订单，对应金额冻结，禁止释放该部分。
- `released`/`closed`：终态，剩余预留为 0，不可再 consume/release。

## 2. 预算分支规则（本次新增的核心）

### 2.1 正常路径（V1.1 已给，保留）

初始 `200000/200000/0` → reserve 30000 `200000/170000/30000` → consume 28000 `172000/170000/2000` → release 2000 `172000/172000/0`。

### 2.2 预留超额（V1.1 已给）

`available=200000` 时申请 reserve 250000 → 拒绝，三值不变，不留预留记录。

### 2.3 超预留消费（V1.1 已给）

预留 30000 后对该预留 consume 30500 → 拒绝（`reserved` 不足）；不得用其他预留或可用余额填补，不自动改扣 `available`。

### 2.4 下单前中断（G12，新增明确步骤）

适用于：已 reserve、**尚无任何订单进入网关**（无 running/unknown 的 merchant.order）。

1. 取消该计划下所有**未领取**的 scheduled 任务（`cancel_task`，仅 scheduled 可取消）。
2. 阻止网关尚未执行的后续步骤。
3. 服务端核实：不存在 running/dispatched/unknown 的订单操作。
4. 满足后 `release_reserved` 全额，预留置 `released`。
- 若存在 running/unknown，转入 2.5，不得整额释放。

### 2.5 部分订单成功 + 部分结果未知（G12 / G05 核心，新增）

> 待B确认：以下保留原稿以定位冲突，不作为通过预期。unknown不能说明事务未提交；已提交订单和扣款不得在核实后重复consume。请分别给已提交/未提交分支的余额与剩余预留。

**原则（B 定版）：**

1. 写后结果不确定（RESULT_UNKNOWN）时，对应订单**不做 consume、不做 release**，其金额在预留上标记 `frozen`；先 `operation.get` 核实，禁止当 failed 后再扣一次（G05）。
2. **可立即释放**的，只有“属于明确不再执行、且没有任何 running/unknown 操作绑定”的订单金额；服务端按订单逐笔判定。
3. **不可释放**的，是已 succeeded 待 consume 之外的、绑定到 running/unknown 订单的金额。
4. **无法逐笔拆分归属**时（合并订单、金额待定、unknown 金额无法对应到预留子项）：剩余预留**全部冻结**，内部记录可释放金额为0；公开data不得增加released_minor，待人工核实，不按比例猜算。
5. 已 succeeded 的订单：先 `consume_reserved` 落账；已核实 failed/确认未执行的订单：其预留金额解冻，可随剩余一起 release。
6. 已实际下单的订单不能靠改任务/预留状态“回滚”，转人工接管（G12）。

### 2.6 并发不超用与半笔（G06）

- reserve / consume / release 与订单记录、账本、幂等结果、审计在**同一写事务**（SQLite `BEGIN IMMEDIATE` 串行写 + 保存点）。
- 每个记账子动作独立 `posting_key`；同键同内容重放原回执，同键不同内容 `IDEMPOTENCY_CONFLICT`。
- “扣款（consume_reserved）后保存订单失败”：保存点整体回滚，订单与资金都不留半笔；回滚后三值恢复到该子动作之前。
- 账户余额检查在最终授权的同一写事务内、`consume_reserved`/`debit` 落账时进行；`reserve` 阶段只校验 `available` 是否够预留。

## 3. 预算手算（逐场景，单位：分）

| 步骤 | 动作 | balance | available | reserved |
|---|---|---:|---:|---:|
| A0 | 初始 | 200000 | 200000 | 0 |
| A1 | reserve 30000 | 200000 | 170000 | 30000 |
| A2 | 用户取消计划，无订单在途，release 30000 | 200000 | 200000 | 0 |

### 3.2 场景 B：多订单，部分成功、剩余放弃（无未知）

预留 30000 = 鲜花 18000 + 蛋糕 12000。

| 步骤 | 动作 | balance | available | reserved |

> 待B确认：以下保留原稿以定位冲突，不作为通过预期。unknown不能说明事务未提交；已提交订单和扣款不得在核实后重复consume。请分别给已提交/未提交分支的余额与剩余预留。

- 三值保持 `200000/170000/30000`，预留整体 `frozen`，30000 全部冻结直到人工核实。
- 禁止按比例或按猜测释放任一部分。

### 3.5 场景 E：预留超额 / 超预留消费（拒绝，无变化）

| 超预留消费 | reserved 30000，consume 30500 | 拒绝，`200000/170000/30000` 不变 |

## 4. 定时任务规则（transfer.schedule / 到期商户下单）

### 4.1 run_at 合理未来范围（B 定版数字）

- 下界：`run_at ≥ 当前上海时间 + 1 分钟`；更近视为“立即”，拒绝（`INVALID_REQUEST`），避免用 schedule 绕过同步执行与授权。
- 上界：`run_at ≤ 当前上海时间 + 30 天`；更远拒绝（本轮不做生产式长期授权）。
- `run_at` 必须带时区，按上海 UTC+8 展示；登记时不扣款、不占当日累计、不做余额冻结（定时转账本身不 reserve）。
- 商户生日任务的 `run_at`（下单时间）与 `deliver_on`（配送日期）分开；`deliver_on` 不早于 `run_at` 的上海日期。

### 4.2 迟到处理（B 定版：一次性 5 分钟宽限）

定义迟到 = 调度器实际处理时刻 `now > run_at`（服务未运行/重启/派发延迟）。

| 情形 | 处理 |
|---|---|
| `now < run_at` | 未到点，继续等待，不领取、不执行 |
| `now = run_at` | 原子领取 scheduled→running，再进入 execute |
| `0 < now − run_at ≤ 5 分钟` | **自动补执行一次**：`scheduled→running` 后正常重走 execute，按补执行时刻重验；不新建任务、不跳过授权、不预扣 |
| `now − run_at > 5 分钟` | 到期任务原子领取 `scheduled→running` 后置 `failed`（原因 `lateness_expired`），**不静默补单、不扣款**；页面提示重新发起 |
| 已 `running` 后崩溃 | 不按迟到判定，按 4.4 恢复（先查稳定执行键与原操作） |

- 宽限只解决“派发稍晚”，不延长授权：补执行仍需当场确认/验证；商户下单 `merchant.order` 始终红色强验证，不因定时降低权限。
- 5 分钟为一次性窗口，不随重试滚动；补执行仍需当场确认/验证。

### 4.3 到期重验（G11）

- 到点（或宽限内补执行）把 payload 中的完整写请求重新走 `execute`：重新校验**当日**累计（上海）、实时余额、账户/收款人归属、本次授权。
- 动态分级按到期时刻重新计算：登记时是 confirm，到点若当日已成功累计使总额跨入 verify 区间，则到点要求 verify（与转账授权升级同口径）。
- 登记为 scheduled 不预扣、不占累计；到期缺有效确认/强验证 → 业务停在 `awaiting_confirmation/verification`，**不扣款**。
- 业务挑战 10 分钟未确认即 `AUTH_EXPIRED`，该笔不执行；调度任务保持 `dispatched`（已派发终态），需用户重新发起，不得自动续期。

### 4.4 重复触发、重启与恢复（G11）

- 每个任务有稳定 `task_key`；领取用数据库原子条件 `scheduled→running`，并发调度/重复触发只有一个成功，不产生第二笔。
- 到期执行使用**独立且固定**的执行幂等键（≠登记键）；所有重试复用它，重放返回原结果，不二次扣款。
- 重启后扫描：
  - `scheduled` 且 `run_at` 已到 → 按 4.2 宽限判定补执行或 failed。
  - `running`/`unknown`（崩溃在途）→ 先查稳定执行键与原操作（operation.get）：已 dispatched 不重复执行；unknown 先核查再决定，禁止直接重新发起新业务。
- 任务与执行共用 `trace_id`；多步生日每步用独立稳定 task_key 与执行键。

### 4.5 取消与配送日

- `cancel_task` 只能取消未领取的 `scheduled`；对 `running/dispatched/unknown` 返回 `INVALID_STATE`，先核实原执行结果，不伪装成已取消。
- 因重启/延迟发现 `deliver_on` 已过 → 交用户重新确认，不静默补单（契约已有，B 确认）。
- `dispatched` 只代表任务已交给执行网关，不代表扣款成功或验证完成；页面用 operation.get 取真实业务状态再展示确认卡片。

## 5. 定时手算（单位：分）

### 5.1 场景 F：正常到期 + 动态升级 + 迟到

9/16 登记 9/18 09:00 转账 60000（600 元），付款账户 A 初始 200000。

| 时点/情形 | 处理 | balance | 当日累计 | 任务状态 |
|---|---|---:|---:|---|
| 9/16 登记 | scheduled，不扣款不占累计 | 200000 | 0 | scheduled |
| 9/18 09:00 到点（当日已成功 0） | scheduled→running→execute；返回业务待确认 | 200000（未确认不扣） | 0 | dispatched（业务awaiting_confirmation） |
| 用户当场确认成功 | consume/debit 60000 | 140000 | 60000 | dispatched |
| 变体：到点当日已成功累计 80000 | 80000+60000=140000>100000 → verify，未验证不扣 | 待B说明80000的付款账户及期初 | 80000 | dispatched（业务awaiting_verification） |
| 变体：09:03 才恢复（迟到 3 分） | ≤5 分，补执行，按 09:03 重验，其余同上 | 确认后 140000 | 60000 | dispatched |
| 变体：09:06 才恢复（迟到 6 分） | >5 分，failed/lateness_expired，不扣款，提示重发 | 200000 | 0 | failed |

### 5.2 场景 G：到期未确认过期

9/18 09:00 到点进入 confirm，用户 10 分钟内未确认 → 挑战 `AUTH_EXPIRED`，转账不执行、余额不变（200000），任务 `dispatched`；用户仍需转账时重新发起新任务（新幂等键）。

## 7. 本轮明确不做（边界）

- 不做无人值守资金交易：到期/补执行都要当场确认或强验证，不预扣、不静默补单。
- 不做生产式长期授权：run_at 最远 30 天；超过需另立规则。
- 不按猜测释放 unknown 预留，不按比例拆分无法归属的预留。
- 定时转账登记不做余额冻结（与生日预算 reserve 区分）；生日链路的商品/价格/地址素材仍由 E 提供，规则数字不代替素材。
- 本文所有数字为编码前规则预期；A 实现后由 B 在固定版本上独立实测留证，A 的自动测试不替代 B 独立验收。
